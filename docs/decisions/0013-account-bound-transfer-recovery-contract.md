# ADR0013 — Account-bound transfer recovery contract

Status: CP15 design and synthetic contract proof; no Drive API operation or
personal media transfer.

The owner selected Google Drive and authorized a native flow to choose/sign into
an account. CP13 proves recovery for generated bytes in a temporary harness; it
does not model a request that remains in flight while Still is cancelled,
restarted, or switched to a different Drive account. Before implementing the
provider adapter, Still needs a durable attempt identity and explicit uncertainty
rules for asynchronous transfers.

## Decision

Add an isolated provider-neutral transfer ledger/protocol model that binds every
attempt to the connection epoch captured when it was created, the immutable source
version and component-set revisions, destination, and operation key. Persisted
acknowledgements are monotonic and may advance only when the provider confirms
the expected session and offset. A locally expired lease, cancellation, or
process restart never proves that an outstanding provider request stopped.

After an ambiguous create/append/finalize result, mark the attempt uncertain and
reconcile against its existing provider operation/object identity before retrying.
Never create a replacement object while completion is unknown. A response from an
old epoch, stale attempt revision, wrong session, wrong offset, or changed source
cannot advance the current record. Email and display name are never account keys.
The connection epoch is an opaque fence only; reauthorization creates a fresh
epoch, and old jobs cannot be retargeted to it.

The proof admits only one durable attempt for an owner's exact immutable source,
version, source revision, component-set revision, component ID and component
revision tuple. This uniqueness ignores destination, epoch and declared length:
CP14 cannot prove whether a later epoch or destination identifies the same Google
account, and a source cannot be retried elsewhere while the earlier operation is
ambiguous. Historical idempotent replay is allowed. A settled not-applied response
continues through the original attempt and operation identity. CP15 does not model
explicit duplicate-copy intent; a later product contract may add that only with a
provider-level identity and reconciliation policy.

Keep this proof synthetic and disconnected from Android startup, product UI,
provider APIs, network, schedulers and production bootstrap. It may model opaque
provider handles, but must not retain credentials, resumable URLs, raw media,
phone URIs/paths, email or object contents. Do not claim upload, verification,
durability, restore, or deletion capability. No new runtime dependency or changes
to existing databases are permitted.

## Required fault evidence

Prove account switch/disconnect fencing, late completion after cancellation or
restart, duplicate operation replay, ambiguous object creation/finalization,
unknown-offset reconciliation, backwards/skipped acknowledgements, wrong provider
session, stale source/component revision, lease expiry with an outstanding request,
and concurrent expected-revision conflict. Preserve uncertainty until provider
state is resolved; exhausting local retries is not provider failure proof.

## Consequences and exclusions

CP15 prepares the durable protocol for a later Drive adapter; it does not finish
Stage 2 backup. Real transfer still requires the configured OAuth client, source
fidelity/component authority, a visible Drive folder, resumable-upload semantics,
quota and cancellation review, and exact-device/account acceptance. Restore,
automatic policy, verification, local removal and free-space actions remain
separately gated. Rollback removes only the new development proof module and
test wiring; existing media and stores are untouched.
