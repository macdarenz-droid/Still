# ADR 0017: Drive resumable transfer protocol proof

Status: CP20 design; generated fixtures only; not a product transfer capability.

## Context

CP15 models asynchronous transfer recovery, CP16 proves generated-source
snapshot acquisition, CP18 composes those generated proofs, and CP19 checks
current read access to Drive account metadata. None proves Google Drive's
resumable upload wire protocol. Before Still can expose a backup action, it
needs a provider-specific proof of chunk acknowledgement, ambiguous outcomes,
and exact-byte readback.

The next proof is deliberately isolated from user media and the Android product
flow. The Drive guide documents a resumable session URI, chunks in 256 KiB
multiples except for the final chunk, `308 Resume Incomplete` acknowledgements,
status queries, and `200`/`201` completion. It also documents session expiration.

## Decision

Add a pure Kotlin protocol state machine and strict request/response parsing for
one generated binary object. Tests inject a fake transport and generated bytes.
There is no live HTTP implementation, OAuth token, UI entry point, Android
permission change, persistent session, or production backup capability.

The proof covers:

- Initiation response validation, including a bounded HTTPS Google session URL.
- Aligned chunk request ranges, exact lengths, final-chunk behavior, and
  acknowledgements that never advance beyond the submitted bytes.
- `308` range parsing and status-query construction. A missing range means no
  bytes are confirmed. Malformed or contradictory progress becomes unknown.
- Lost responses and transient errors: query the existing session before
  retransmitting. Never create a replacement session or object from an
  ambiguous outcome.
- `200`/`201` completion metadata followed by a bounded generated-object
  readback. Completion is verified only when byte count and SHA-256 match the
  exact generated source bytes.
- Expired sessions and unresolvable state remain blocked for reconciliation;
  this proof does not guess whether an object exists or create a duplicate.
- Account-epoch changes, cancellation, unsafe URLs, redirects, oversized or
  malformed responses, wrong metadata, truncated readback, and byte mismatch.

The resumable session URL is treated as a secret capability: never render,
persist, or log it. HTTP authorization remains outside this protocol proof.

## Exclusions and limits

This is not a visible backup feature and does not upload generated or personal
media to Google. It does not establish original-source fidelity, complete
motion/sidecar inventory, durable encrypted session storage, process-death
recovery, duplicate prevention across restarts, live Drive behavior, restore,
or permission to remove phone copies. The app must continue to say that backup
is unavailable. A later product checkpoint must establish those remaining
boundaries and perform configured-account/device validation before exposing
any transfer action.

## Acceptance evidence

- Focused Kotlin tests use only deterministic generated bytes and an injected
  fake transport; they prove the protocol cases above without network access.
- Existing Android tests, strict lint, and debug assembly pass.
- Independent reviewer and separate red team pass the exact integrated SHA.
- Hosted Android and contracts/discovery checks pass on that exact SHA.
- Frontend and SEO audits find no backup control, upload claim, or AI wording.
- Live Google requests, OAuth chooser, device behavior, user media, actual
  backup, and restore remain not run and are not implied by this checkpoint.
